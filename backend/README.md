# Open Door Live — Backend

Supabase-backed backend for the platform: schools, fixtures/scheduling,
sponsors, subscriptions, and the accounts (platform admin / school operator /
parent) that the broadcaster app and the public web platform both talk to.

## What's here

```
backend/
  supabase/
    migrations/
      0001_init_schema.sql   -- full initial schema, RLS, and triggers
```

There's no `config.toml` yet — that gets generated by `supabase init` (see
below) rather than hand-written, since its format is tied to whatever CLI
version you're running.

## Schema overview

- **schools** — one row per school. Publicly readable (the schedule site
  lists them); writable only by platform admins or that school's own
  operators.
- **youtube_accounts** — which YouTube channel a school's fixtures get
  provisioned under. Every school defaults to the platform's own account
  (a `platform`-owned row); a school can be pointed at its own account by
  giving it a `school`-owned row instead — see `schools.youtube_account_id`.
  Never exposed outside platform admins.
- **subscriptions** — one row per school: tier, billing cycle, status
  (trial/active/expired/cancelled). This only ever gates whether a school
  can currently log in / operate / create new fixtures — **it never hides
  past replays**. A lapsed school's existing content stays up; that's a
  deliberate business decision, not an oversight.
- **profiles** — extends Supabase's `auth.users` with a role
  (`platform_admin` / `school_operator` / `parent`) and, for school
  operators, which school they belong to. Every new sign-up becomes a
  `parent` automatically (see the `handle_new_user` trigger) — nobody can
  grant themselves elevated access through the sign-up form. Promoting
  someone to `school_operator` or `platform_admin` is a deliberate admin
  action.
- **teams**, **sponsors** — belong to a school. Sponsors are *school-owned*
  sales inventory (each school sells and manages its own sponsor slots
  under the subscription model), not a platform-wide pool.
- **fixtures** — the schedule/replay data itself. Publicly readable on
  purpose (that's the whole product); writable by platform admins or the
  host school's operators.
- **fixture_broadcast_credentials** — split out from `fixtures`
  specifically so the YouTube stream key is never reachable through the
  same public-read policy as the rest of a fixture. Only platform admins
  and the operator assigned to that specific fixture can read it.
- **fixture_sponsors** — which sponsors are placed on a given fixture, at
  what position/tier, baked into the video vs. web-layer only.
- **notify_subscriptions**, **favourites** — parent-facing "notify me" /
  "follow this team" features. A parent only ever sees their own.

## Getting this running against a real Supabase project

This was authored and validated against a local Postgres instance (schema,
constraints, and RLS policies were all smoke-tested), but no live Supabase
project is connected yet — that needs your own Supabase account.

1. Install the Supabase CLI (see https://supabase.com/docs/guides/cli) and
   run `supabase init` inside `backend/` — this generates `config.toml`
   without overwriting the `migrations/` folder already here.
2. Create a project at https://supabase.com and grab its project ref.
3. `supabase link --project-ref <your-ref>`
4. `supabase db push` — applies `0001_init_schema.sql` to your real project.
5. In the Supabase dashboard, promote your own account to
   `platform_admin` once you've signed up through Supabase Auth (there's no
   seed data for this yet — it has to be the first row you touch by hand):
   ```sql
   update public.profiles set role = 'platform_admin' where id = '<your-auth-user-id>';
   ```

## Edge functions

- **`supabase/functions/provision-fixture-broadcast/`** — calls the YouTube
  Live API to turn a fixture into an actual broadcast (create the event,
  create a fresh ingest stream, bind them, save the results). Fires
  automatically on fixture creation via a database trigger (see the next
  section). See its own README for details, design decisions, and how to
  run its unit tests.

## Fixture creation triggers provisioning automatically

`0002_provision_on_fixture_insert.sql` adds a trigger on `fixtures` that
calls `provision-fixture-broadcast` (via `pg_net`, fire-and-forget) right
after any fixture is inserted — no matter what created it. It needs two
Vault secrets populated once per project before it'll actually do
anything (the function's URL and the service-role key it calls with) —
see the edge function's own README for the exact commands. Until those
are set, fixture inserts still succeed; the trigger just logs a warning
and skips provisioning.

## The Android app now reads from this backend (optional)

The broadcaster app's "CREW SIGN-IN" section (see the top-level README) signs a
crew member in against Supabase Auth, lists their school's upcoming fixtures, and
pulls a selected fixture's RTMP URL/key from `fixture_broadcast_credentials` —
instead of the operator typing them in by hand. It's additive: manual entry still
works exactly as before if nobody signs in, and the feature quietly disables itself
if the app isn't built with a Supabase URL/anon key configured.

Only `school_operator` accounts get a fixture list right now (a `platform_admin`
signing in from the app sees none — no school-picker exists yet for that case).
